# Deterministic CLI baseline

> Historical baseline from 2026-10-07. See [current dev status](dev.md) for the fixes,
> replacement regression tests and refreshed dependency graph.

## Product boundary

Deploy a service, run version-controlled YAML HTTP/JSON checks, and use the exit
code as a deployment gate. Initial work prioritizes authentication, bounded
requests, accurate independent check results, useful diagnostics and secret
handling. Keep existing syntax where practical. No UI rewrite, hosted service or
new protocols are part of this effort. This is a development baseline, not a
production-ready release.

### Runner maintenance decision

Keep 2.0.0/0.3.5 unchanged in this PR to establish the current contract. This is
not a security endorsement: see [the exposure review](security-baseline.md).
No second source tree is vendored and no runner fork or package is published.

Prefer an upstream release if it contains the required fixes and passes our
package regressions. Published runner 2.0.7 still has the shared JSONPath catch and
unsafe matcher behavior. More importantly, the published 2.0.7 tarball still
requests JSONPath 7.x, while current source moves it to 10.3.x without changing the
2.0.7 manifest version. Merely upgrading the CLI to published 2.0.7 will not deliver
that source dependency fix. This is a concrete example of why a source manifest
version does not prove a fix ships.

For phase two, recommend a companion runner fork if upstream has not released the
fix: preserve history, keep a small patch series, build/test from a pinned source
commit, and consume an immutable version under a controlled npm scope using an
npm alias for `@stepci/runner`. Pin its exact version/integrity and record its
source revision in release evidence. Publishing that package requires approval.
A Git SHA dependency without verified generated `dist` is insufficient; avoid
install-time patching or copying runner sources into this repository. An upstream
release that meets the regressions lets us retire the fork.

## Reproduce from a fresh checkout

Use Linux with Git, tar and the [Node 24 LTS line](https://github.com/nodejs/Release).
This baseline is tested on Node **24.21.0** and npm **11.9.0**. Runtime engines
allow later Node 24/npm 11 patches; build scripts require the exact selected
versions. The older TypeScript Node16 target is retained as a compilation target,
not a claim of supported Node16 runtime. Change pins deliberately in a tested PR.

```sh
git clone https://github.com/rclevenger-hm/stepci.git
cd stepci
git checkout baseline/deterministic-cli
nvm install
nvm use
npm install --global npm@11.9.0
npm ci --no-audit --no-fund
npm run verify
git diff --exit-code -- schema.json package-lock.json
```

`npm ci` downloads build dependencies from npm; the **test workloads** require no
public services. They bind an ephemeral loopback port, use fake credentials and
run the compiled CLI as a separate process in a temporary directory. Each child
gets a minimal environment with analytics disabled, no inherited credentials or
proxies, a loopback TCP guard, and a ten-second kill deadline. Individual HTTP
requests have a two-second timeout (300ms for the deliberate timeout case) and
zero retries. These bounds are fixture settings,
not newly introduced application defaults. The TCP guard is test instrumentation,
not a sandbox for running untrusted workflows.

The suite covers status/JSON success, a deliberately broken 503 deployment,
incorrect JSON, bearer authentication, missing authentication, YAML errors,
structurally invalid workflows, missing files, invalid CLI options, connection
refusal, peer disconnect and a server that never responds. Assertion failures
include captured diagnostics. The existing workflow syntax is used unchanged.

| Observed outcome | CLI exit code |
| --- | --- |
| All checks pass | 0 |
| A check fails, connection errors, or request timeout | 5 |
| YAML parse error, missing tests/file, invalid CLI option | 1 |

Treat **any nonzero** as a failed gate. Code 1 currently includes uncaught runner
errors; it is not yet a stable taxonomy of all validation failures. Schema
generation provides editor metadata, not runtime validation. Malformed workflows
currently produce technical stack traces rather than polished diagnostics.

### Packaging and evidence

`npm run package` cleans/rebuilds `dist`, regenerates `schema.json`, verifies the
installed graph, and stages a tarball with **npm-shrinkwrap.json copied from the
source package-lock.json**. The staging directory is deleted afterwards. There
is one tracked lock, not two competing source locks. npm excludes ordinary
package-lock.json from published packages, so shipping only that lock would not
lock consumer installations. Direct `npm pack` intentionally stops with guidance
to use the packaging command.

The supported baseline artifact install is **extract, then `npm ci`**:

```sh
npm run package
preview_dir="$(mktemp -d)"
tar -xzf artifacts/stepci-2.8.2.tgz -C "$preview_dir"
cd "$preview_dir/package"
npm ci --omit=dev --ignore-scripts --no-audit --no-fund
node scripts/provenance.cjs verify .
STEPCI_DISABLE_ANALYTICS=1 node dist/index.js --help
```

An isolated `npm install ./stepci-2.8.2.tgz` experiment with npm 11.9.0 tried to
resolve newer transitives despite the included shrinkwrap and failed offline
with ENOTCACHED. Do **not** use that installation method as evidence of a locked
application. Registry installation must be tested separately as part of the
approved release process; it is not certified by this baseline.

`npm run test:package` builds twice, compares build manifests and npm tarball
SHA-256 hashes, extracts the tarball into an isolated directory, installs its
production dependencies with **offline `npm ci`**, and runs the same baseline and
known-defect tests there. The offline install uses the cache populated by the
source `npm ci`; it cannot refresh
dependency ranges. No registry package is published. A test also alters runner
executable bytes and the generated schema and requires verification to reject both.

Evidence is written under `artifacts/` and `dist/build-manifest.json`:

- Source commit plus source/build-script hashes, exact Node/npm versions and lock
  hash. A source commit alone does not imply a clean tree; release checks must
  require one.
- Runner/plugin package byte hashes, entrypoints, versions, tarball URLs and SRI.
- Every production dependency's locked version/integrity, checked against the
  installed graph using the CLI's module resolution.
- Generated schema and compiled CLI hashes, package inventory, tarball checksum,
  and verification results.

This is inspectable provenance, not a signed supply-chain attestation. The tests
prove identical npm tarballs for two builds on the same toolchain/environment;
they do not establish cross-platform or container image reproducibility. CI saves
the evidence as a workflow artifact with read-only repository permissions.

## Existing failures and release blockers

| Finding | Baseline treatment / next phase |
| --- | --- |
| Original `npm test` required absent `workflow.yml` and failed ENOENT | Replaced with fixture suite; manual command preserved as `test:manual` |
| Generated schema differed from checked-in schema | Regenerated from runner 2.0.0, removing unsupported `before`/`after` properties; CI rejects future drift |
| Original lock root version stale; 38 entries lacked URL/integrity | Corrected root metadata; filled metadata for the same registry versions, without upgrading the graph |
| #259 overwrites passing JSONPath results | Explicit known-defect characterization; fix belongs in runner phase two |

| Invalid workflow yields TypeError | Exit 1 verified; runtime validation and bounded, redacted diagnostics remain open |
| Telemetry enabled by default | Disable with `STEPCI_DISABLE_ANALYTICS=1`; behavior detailed below |
| Dependency vulnerabilities | Reviewed separately; no audit-fix sweep or assertion of release readiness |
| Local tarball dependency install ignored shrinkwrap in npm 11.9.0 | Supported artifact path uses extraction and `npm ci`; registry/global install equivalence remains a release gate |
| Docker/Action floating inputs, caches and eval | No container runtime was available locally; delivery-path equivalence remains unverified and blocks release |

`npm run test:known` intentionally asserts current defects, with `KNOWN BUG` /
`KNOWN LEAK` in each name. A green characterization means the defect is reproduced,
not resolved. When implementing a fix, replace it with desired-behavior regressions;
do not skip it, invert all expectations indiscriminately, or present it as acceptance.

The old push workflow ran the Docker Action against `examples/status.yml` and a
public endpoint. It is replaced by this baseline workflow. That is not proof that
the reusable Action works.

### Documentation CI

The separate `Build documentation` workflow checks pull requests and pushes to
`main`, using the same pinned Node/npm versions and `npm ci`. It builds VitePress,
rejects lock/schema drift and retains the static site as the `documentation-site`
workflow artifact for seven days. Reproduce locally with `npm run docs:build`
after the locked installation above; preview with `npm run docs:serve`.

The inherited Pages workflow failed during action setup because
`upload-pages-artifact@v1` depends on the retired `upload-artifact@v3`. It has been
replaced with a build-only check and a pinned artifact action. No GitHub Pages
configuration, deployment environment or hosting credentials are needed. The
workflow has read-only repository permissions and does not publish a site.
Enabling hosting is a separate, approved change that must also review the site's
base path, upstream navigation/assets and search configuration. The existing
Docker publication workflow is release-triggered and still subject to the
delivery/release gates below.

### Telemetry and secret handling today

`src/lib/analytics.ts` creates a persistent random UID through `conf` at import
time and initializes PostHog even when analytics is disabled. When enabled, it
sends a `ping` to `https://eu.posthog.com` with UID, OS type, Node version, the first
command argument and environment label (CI/local/Docker). The explicit payload
does not contain workflow bodies or secret values; the upstream README lists CLI
version but this implementation does not explicitly add it. Inspecting code is
not a full wire-level privacy audit. Any nonempty `STEPCI_DISABLE_ANALYTICS`
disables capture and the notice, including the string `false`; prefer `1`.
Config directory writes and client initialization still happen. Tests verify no
non-loopback TCP attempt with the flag set; phase two should test enabled and
disabled lifecycle behavior explicitly and decide the self-hosted default.

The `--secret` option templates values; it does **not** currently guarantee log
redaction. CLI arguments can also be visible to process inspection. Until phase
two, use disposable local credentials and do not upload sensitive diagnostics.
There are no report exports added here. Any later export must share the same
redaction contract and be tested through the packaged CLI.

## Phased work (roughly four weeks, evidence-driven)

1. **Baseline, this draft:** locked toolchain/install, local compiled/package
   tests, generated schema consistency, dependency/exposure review and provenance.
2. **Runner correctness/security:** select tested runner release or companion
   fork; reproduce then fix #259 with credited upstream work, missing/null/empty/
   wrong-type/invalid-expression/mixed-result matrix and explicit negative matcher
   rules. Address exposed dependencies, secrets across normal/verbose/errors/
   reports, telemetry and input diagnostics. Prove fixes in the packaged CLI.
3. **Delivery and releases:** pin image digests and npm, locked multistage builds,
   remove caches from final layers, replace eval with argv handling, forward inputs
   correctly. Run fixture cases plus spaces/quotes/metacharacters/signals through
   package, Docker and reusable Action. Compare two clean image builds and inspect
   differences. Add dependency checks and signed provenance to approved releases.
4. **Pilot and adoption:** confirm staging/local environment and access for one
   or two existing services before touching them; demonstrate a broken deployment,
   write migration/troubleshooting/release guides. Review PR258 before multi-file
   additions. Add exports/integrations only for a demonstrated pilot need.

Each phase has small tested draft PRs. Preserve upstream authorship, history and
MPL notices; review source-distribution obligations before release. Release gates
include no unexplained artifact differences, no fixture secrets in any output,
equivalent results across delivery paths, reviewed vulnerability exposure and a
second developer reproducing the quickstart. Merge, production access,
deployment and publication require owner approval.
